# D-A5-5: Frontend — streamed investigation console

## Context

The API (Phase 5) exposes `POST /investigations` plus a polling
`GET /investigations/{id}` and a streaming `GET /investigations/{id}/events`
(SSE). The frontend needs to let a visitor trigger an investigation and watch
it progress node-by-node, and — critically — needs to make the Phase 4
evidence/honesty guardrail visible rather than hiding it behind a plain
"answer" box.

## Decision

A minimal Next.js (App Router) app, closer to `disruption_router/frontend`'s
plain-inline-styles simplicity than `clinical_care_navigator/frontend`'s
Tailwind/Zod/component-heavy build, since A5 has no review queue or HITL flow:

1. **Scenario picker, not a bare text box.** `src/app/page.tsx` offers six
   preset questions mapped onto the five seeded incidents plus the
   adversarial fixture in `data/generate_logs.py`, so a first-time visitor
   sees a real run (with real retrieved evidence) before typing anything, and
   can reach the guardrail's refusal path with one click.
2. **Native `EventSource` for streaming**, not a hand-rolled fetch-stream
   reader — `src/lib/api.ts`'s `streamInvestigationEvents` mirrors the
   sibling `clinical_care_navigator` convention. A terminal `{node:
   "__end__"}` event closes the stream and triggers a single
   `GET /investigations/{id}` fetch for the final `IncidentReport`, rather
   than trusting the stream's own final payload — the run store is the
   source of truth.
3. **Types come from the OpenAPI schema, not hand-written mirrors.**
   `src/lib/types.ts` re-exports aliases over `src/lib/api-types.ts`
   (generated by `make frontend-types` / `npm run gen:types`, wired into the
   Makefile since Phase 0). `IncidentReport` is a real typed Pydantic
   response model here (unlike the navigator's opaque LLM answer blob), so
   generated types are strictly better than a hand-maintained duplicate.
4. **`ReportPanel` surfaces `insufficient_evidence` as a first-class state**,
   not an edge case: a red banner explains it is "a deliberate refusal to
   guess, not a failed run" whenever the guardrail downgrades a report —
   this is the frontend's main job in making Phase 4's decision legible.
5. **Playwright e2e (`e2e/incident.spec.ts`) fully mocks the API** via
   `page.route()`, covering loading/streaming/success/insufficient-evidence/
   empty/error states without a live backend or LLM. `e2e/capture-
   screenshots.spec.ts` reuses the exact same fixtures to produce the docs
   screenshots, so a screenshot can never silently drift from what the smoke
   test proves the UI does — matching the navigator's convention.

## Consequences

- No CSS framework or state-management library — the whole UI is three
  components plus a fetch/SSE wrapper, appropriate for A5's scope.
- The generated `api-types.ts` must be regenerated (`make frontend-types`)
  whenever `oncall.api.schemas` or `oncall.schemas.models` change; a stale
  file only causes a local type-check failure, not a runtime bug, since the
  backend is the actual source of truth.
- Playwright's full network mocking means the e2e suite never depends on
  `OPENAI_API_KEY` or a running Docker sandbox, so it can run in CI or a
  contributor's machine unconditionally.
